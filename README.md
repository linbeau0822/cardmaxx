# CardMaxx

CardMaxx is a personal credit-card spending analyzer and recommendation engine.
It connects a user's financial accounts through [Plaid](https://plaid.com),
imports their transaction history, categorizes and aggregates their spending,
calculates the rewards their current cards actually earn, and identifies the
cards — or combinations of cards — that would earn them more.

The core philosophy is **deterministic financial calculations first, AI
explanations second**. Every number CardMaxx reports comes from explicit,
testable arithmetic over real transactions. An LLM may later put that reasoning
into words; it never produces the numbers.

## Motivation

This project exists to build a real fintech application end to end rather than a
demo. Specifically, it is a vehicle for:

- building a real-world financial application on real transaction data
- integrating a production financial API (Plaid) with its tokens, cursors and failure modes
- modeling messy transaction data into something that can be reasoned about
- designing a deterministic, explainable recommendation engine
- exploring portfolio optimization: combinations of cards under annual fees, category caps and opportunity cost
- demonstrating backend engineering in Go — API design, data modeling, SQL, algorithms
- eventually incorporating AI in a well-defined supporting role rather than as the product

## Current Status

**Phases 1-6 are done**, backend and frontend. The dashboard connects real
accounts via Plaid Link, syncs transactions, and shows spending analysis, the
user's matched cards, and portfolio recommendations.

What works today:

- Go API server with routing, structured logging, graceful shutdown, and a functional `GET /health`
- PostgreSQL schema for users, Plaid items, accounts, transactions and the credit-card catalog, applied by versioned migrations
- Type-safe query layer generated by sqlc
- A real Plaid client (`internal/plaid`): Link token creation, public-token exchange and cursor-based transaction sync against the Plaid API
- `PlaidService` (`internal/service`): links a Plaid Item to the implicit current user, pages through `/transactions/sync`, upserts accounts and transactions, and auto-links an account to a catalogue card when its name unambiguously names one
- `POST /api/v1/plaid/link-token`, `/exchange-token`, `/sync` and `GET /api/v1/accounts`, `/transactions` are live, backed by PostgreSQL
- React + TypeScript dashboard that talks to the Go API
- Docker Compose for PostgreSQL, a Makefile for every common task, and CI

There is still no authentication (by design, until Phase 8) and no AI yet.
The reward/annual-value math (`internal/reward`) is wired to a user's own
accounts via `PATCH /api/v1/accounts/{id}` and `GET /api/v1/cards/{id}/value`
(Phase 4c). `GET /api/v1/recommendations` (Phase 5) builds on that: it ranks
catalogue cards the user doesn't hold by the incremental annual value each
would add on top of their current cards - what the card would capture in
spend categories where it beats what they already have, net of its annual
fee, not its value in isolation. `GET /api/v1/recommendations/portfolio`
(Phase 6) generalizes this to whole combinations: for every portfolio size
from 1 card up to the catalogue size, it brute-forces every combination
(the catalogue is small enough that this is cheap) and finds the one with
the highest net value - rewards earned across the set, with spend that
overflows one card's bonus cap now routed to the next-best card in the set
rather than falling back to that same card's base rate, minus the
combination's total annual fees. Each size also reports its marginal value
over the best smaller size, so the dashboard can show exactly where adding
another card stops paying for its own fee.

The frontend opens the real Plaid Link widget via `react-plaid-link` from the
"Connect Account" button, and POSTs its `public_token` to `/exchange-token`
on success. Each sync tries to auto-match a credit account's name to a
catalogue card (issuer and product both named, unambiguously); every Plaid
Sandbox test account and some real ones don't match anything, so the "Your
Cards" panel offers a manual picker for whatever's left unmatched, backed by
`PATCH /api/v1/accounts/{id}`.

## Architecture

```text
                    ┌───────────────┐
                    │ React + TS    │
                    │ Frontend      │
                    └───────┬───────┘
                            │
                         REST/JSON
                            │
                    ┌───────▼───────┐
                    │ Go + Chi      │
                    │ API           │
                    └───────┬───────┘
                            │
                    ┌───────▼───────┐
                    │ Services      │
                    │ & Business    │
                    │ Logic         │
                    └───────┬───────┘
                            │
                    ┌───────▼───────┐
                    │ PostgreSQL    │
                    └───────────────┘

                    Go Backend
                         │
                         ▼
                    ┌───────────────┐
                    │ Plaid API     │
                    └───────────────┘
```

Each request flows in one direction:

```text
HTTP handler   internal/api         decodes the request, writes JSON, no SQL
     ↓
(service)                           business rules — added per phase, see below
     ↓
Repository     internal/database/db generated sqlc queries
     ↓
PostgreSQL
```

The middle layer is parenthesised because it is empty today. When a handler
needs business rules, the service is born then, in its own package, taking a
**narrow repository interface that it declares itself** rather than a database
handle — which keeps the SQL each package may run visible in one place and
makes it testable with a small fake instead of a live database.

External services sit behind their own boundary:

```text
Plaid API  →  plaid.Client   HTTP transport, wire-format conversion
           →  application    sees CardMaxx domain types only
```

Nothing outside `internal/plaid` imports a Plaid type, and Plaid access tokens
never leave the backend.

## Tech Stack

### Backend

| Technology | Role |
| --- | --- |
| **Go** | API server and all financial logic |
| **Chi** | HTTP routing and middleware; a thin layer over `net/http` rather than a framework |
| **PostgreSQL** | Source of truth for accounts, transactions and the card catalog |
| **pgx** | PostgreSQL driver and connection pool |
| **sqlc** | Compiles `sql/queries/*.sql` into type-safe Go; queries stay real SQL, no ORM |
| **golang-migrate** | Versioned, reversible schema migrations |
| **log/slog** | Structured JSON logging, correlated by request id |
| **Plaid API** | Account linking and transaction data (sandbox) |

### Frontend

| Technology | Role |
| --- | --- |
| **React + TypeScript** | Dashboard UI |
| **Vite** | Dev server and bundler; proxies the API in development |
| **Tailwind CSS** | Styling |

### Development

| Technology | Role |
| --- | --- |
| **Docker Compose** | Local PostgreSQL |
| **Make** | Discoverable entry point for every task (`make help`) |
| **GitHub Actions** | Formatting, vet, tests, builds, and migration up/down against real PostgreSQL |

The backend has exactly three direct dependencies (Chi, pgx, google/uuid).
Everything else is the standard library.

## Local Development

### 1. Required software

| Tool | Version | Notes |
| --- | --- | --- |

### 2. Environment variables

```bash
cp .env.example .env
```

Then fill in `PLAID_CLIENT_ID` and `PLAID_SECRET` from the
[Plaid dashboard](https://dashboard.plaid.com/developers/keys) (sandbox keys).

| Variable | Required | Default | Description |
| --- | --- | --- | --- |
| `DATABASE_URL` | yes | — | PostgreSQL connection string |
| `PLAID_CLIENT_ID` | yes | — | Plaid client id |
| `PLAID_SECRET` | yes | — | Plaid secret for the selected environment |
| `PLAID_ENV` | no | `sandbox` | `sandbox` or `production` |
| `SERVER_PORT` | no | `8080` | HTTP listen port |
| `CORS_ALLOWED_ORIGINS` | no | `http://localhost:5173` | Comma-separated browser origins |
| `POSTGRES_PORT` | no | `5432` | Host port for the Compose database |

The server validates configuration at start-up and reports **every** missing or
invalid variable at once:

```text
invalid configuration:
  - DATABASE_URL is required
  - PLAID_CLIENT_ID is required
```

`.env` is gitignored. Never commit real credentials.

> If you already run PostgreSQL on port 5432, set `POSTGRES_PORT=5433` and point
> `DATABASE_URL` at `localhost:5433`; otherwise the local server shadows the
> container.

### 3. Start PostgreSQL

```bash
make db-up          # docker compose up -d --wait postgres
```

### 4. Run migrations

```bash
make migrate-up     # apply all pending migrations
make migrate-down   # roll back the most recent migration
make db-reset       # destroy the volume and rebuild a migrated, empty schema
```

### 5. Start the backend

```bash
make dev            # db-up + migrate-up + run the API server
# or just the server:
make dev-backend
```

```bash
curl -s localhost:8080/health
# {"status":"ok"}
```

### 6. Start the frontend

```bash
make setup          # first time only: go mod download + npm install
make dev-frontend   # http://localhost:5173
```

Vite proxies `/api` and `/health` to `localhost:8080`, so the browser only ever
talks to one origin.

### 7. Run tests

```bash

make lint           # gofmt check + go vet + frontend lint

```

## API

Base path for application endpoints: `/api/v1`.

### Available

#### `GET /health`

Liveness check. Dependency-free, so it answers even when PostgreSQL or Plaid is
unavailable.

```http
GET /health  →  200 OK

{ "status": "ok" }
```

#### `POST /api/v1/plaid/link-token`

Requests a Plaid Link token for the current user.

```http
POST /api/v1/plaid/link-token  →  200 OK

{ "link_token": "link-sandbox-...", "expiration": "2026-01-01T00:00:00Z" }
```

#### `POST /api/v1/plaid/exchange-token`

Exchanges a public token from Plaid Link for an access token, and stores the
resulting Item.

```http
POST /api/v1/plaid/exchange-token
{ "public_token": "public-sandbox-..." }

→  200 OK
{ "item_id": "..." }
```

#### `POST /api/v1/plaid/sync`

Pulls new transaction activity for every Item the current user has linked,
paging through Plaid's `/transactions/sync` cursor until it is caught up.

```http
POST /api/v1/plaid/sync  →  200 OK

{ "items": [{ "plaid_item_id": "...", "added": 50, "modified": 0, "removed": 0 }] }
```

#### `GET /api/v1/accounts`

Lists every account linked to the current user.

#### `PATCH /api/v1/accounts/{id}`

Links (or, given a null `credit_card_id`, unlinks) an account to a catalogue
card. Scoped to the current user — an id belonging to someone else, or to no
one, is a `404`. Sync already calls this automatically when an account's
name unambiguously names one catalogue card; this endpoint is for whatever
sync couldn't resolve, or to correct it.

```http
PATCH /api/v1/accounts/{id}  →  200 OK
{ "credit_card_id": "778c8627-c773-4474-93e5-4422e94e8bce" }

{ "id": "...", "credit_card_id": "778c8627-c773-4474-93e5-4422e94e8bce", ... }
```

#### `GET /api/v1/transactions`

Lists the current user's transactions, most recent first.
Query params: `limit` (default 50, max 200), `offset` (default 0).

#### `GET /api/v1/analysis/spending`

Reward-eligible spend by calendar month, by category within one selected
month, and the top 10 merchants by all-time total.
Query params: `month` (e.g. `2026-03-01`; defaults to the most recent month
with activity).

```http
GET /api/v1/analysis/spending  →  200 OK

{
  "months": [{ "month": "2026-09-01", "total_cents": 300938, "transaction_count": 28 }],
  "selected_month": "2026-09-01",
  "categories": [{ "category_name": "FOOD_AND_DRINK", "total_cents": 4899, "transaction_count": 6 }],
  "all_categories": ["FOOD_AND_DRINK", "TRANSPORTATION"],
  "top_merchants": [{ "merchant_name": "Starbucks", "total_cents": 3897, "transaction_count": 9 }]
}
```

#### `GET /api/v1/cards`

Lists the credit-card catalogue, each with its bonus reward categories.
Global reference data — not scoped to any user.

```http
GET /api/v1/cards  →  200 OK

{
  "cards": [
    {
      "id": "778c8627-c773-4474-93e5-4422e94e8bce",
      "name": "Sapphire Preferred",
      "issuer": "Chase",
      "annual_fee_cents": 9500,
      "base_reward_rate_bps": 100,
      "reward_categories": [
        { "category_name": "FOOD_AND_DRINK", "reward_rate_bps": 300, "reward_cap_cents": null },
        { "category_name": "TRAVEL", "reward_rate_bps": 200, "reward_cap_cents": null }
      ]
    }
  ]
}
```

#### `GET /api/v1/cards/{id}/value`

What a catalogue card would earn the current user, based on their
trailing-12-month reward-eligible spend, net of the card's annual fee.

```http
GET /api/v1/cards/{id}/value  →  200 OK

{ "rewards_earned_cents": 48600, "annual_fee_cents": 9500, "annual_value_cents": 39100 }
```

#### `GET /api/v1/recommendations`

Catalogue cards the current user doesn't already hold, ranked by the
incremental annual value each would add on top of their current cards:
what it captures in trailing-12-month spend categories where it beats what
they already have, net of its annual fee. `categories_won` lists which
categories drove that, and the rate each would replace.

```http
GET /api/v1/recommendations  →  200 OK

{
  "recommendations": [
    {
      "card": { "id": "...", "name": "Costco Anywhere Visa", "issuer": "Citi", "annual_fee_cents": 0, "base_reward_rate_bps": 100 },
      "incremental_value_cents": 3838,
      "categories_won": [
        { "category_name": "TRANSPORTATION", "previous_rate_bps": 150, "new_rate_bps": 400 }
      ]
    }
  ]
}
```

#### `GET /api/v1/recommendations/portfolio`

For every portfolio size from 1 card up to the catalogue size (capped at 5),
the combination of catalogue cards with the highest net value on the
current user's trailing-12-month spend: rewards earned across the set
(spend that overflows one card's bonus cap routes to the next-best card in
the set, not just that card's base rate) minus the combination's total
annual fees. `marginal_value_cents` is the net value a size adds over the
best smaller size.

```http
GET /api/v1/recommendations/portfolio  →  200 OK

{
  "options": [
    {
      "cards": [{ "id": "...", "name": "Sapphire Preferred", "issuer": "Chase", "annual_fee_cents": 9500, "base_reward_rate_bps": 100 }],
      "rewards_earned_cents": 48600,
      "annual_fees_cents": 9500,
      "net_value_cents": 39100,
      "marginal_value_cents": 39100
    }
  ]
}
```

### Errors

Every error uses one envelope, with a stable machine-readable `code`:

```json
{
  "error": {
    "code": "not_found",
    "message": "no card with that id"
  }
}
```

Codes: `not_found`, `method_not_allowed`, `not_implemented`, `bad_request`, `internal_error`.

## Data Model

Six tables, applied by `backend/migrations`:

```text
users ──┬─< plaid_items ──< accounts ──< transactions
        │
credit_cards ──< card_reward_categories
```

Two conventions matter:

- **Money is integer cents; reward rates are integer basis points** (1.5% = `150`
  bps). Reward math must be exact and reproducible, so no float is ever
  persisted. Plaid's float dollar amounts are converted to cents at the Plaid
  boundary and never again.
- **Ownership is transitive**: a transaction belongs to an account, which belongs
  to a Plaid item, which belongs to a user. Every read is scoped by user id in
  SQL, so no query can leak another user's spending.

## Design Principles

1. **Financial calculations must be deterministic.** The same transactions and
   the same card rules always produce the same numbers. Integer cents and basis
   points, no floating-point money, no randomness.
2. **AI explains calculations rather than inventing them.** An LLM may describe
   why a recommendation holds; it never computes a reward, a fee or a dollar
   value.
3. **Keep the Go backend idiomatic and maintainable.** Standard library first,
   small packages, explicit dependencies, errors wrapped with context. Code is
   written when a caller needs it, not in anticipation of one: no package, type
   or interface exists here without something that uses it.
4. **Avoid premature infrastructure.** No queue, cache or orchestrator until a
   measured problem demands one. PostgreSQL and a single binary go a long way.
5. **Prefer PostgreSQL and SQL over unnecessary abstractions.** Queries are
   hand-written SQL compiled to type-safe Go by sqlc. There is no ORM and no
   query builder to reason around.
6. **Keep external integrations behind clear boundaries.** Only
   `internal/plaid` knows Plaid exists; it exposes CardMaxx's own types, so it
   can be faked or replaced without touching callers.
7. **Security and privacy are first-order concerns.** This application handles
   financial data: access tokens stay server-side, every query is scoped by
   user, and secrets live only in the environment.
8. **Optimize for maintainability and technical depth, not technology count.**
   The interesting parts of CardMaxx are the data model, the reward
   calculations and the optimization problem — not the size of the stack.
